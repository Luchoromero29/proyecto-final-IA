b) Revisión de consultas y conocimiento recuperable

En el PG3 la valuación pasó de "precio de un equipo nuevo del segmento × depreciación" a una valuación por componentes (precios hedónicos): el valor de un usado se explica por su procesador, su línea y su RAM, no por el modelo exacto. Se relevaron 289 avisos reales de Mercado Libre (9/11/2026) que se cargan en Neo4j como :AvisoMercado y, con medianas calculadas en Cypher, se calibra el valor de cada :Procesador y el factor de cada :Linea (si la línea tiene menos de 3 avisos, usa el de su :GrupoLinea).

Consulta principal — valuación por componentes

    WITH toLower($procesador) AS tp, toLower($texto) AS tt
    OPTIONAL MATCH (p:Procesador) WHERE tp =~ p.patron
    WITH tt, p ORDER BY p.prioridad DESC LIMIT 1
    OPTIONAL MATCH (l:Linea) WHERE tt =~ l.patron
    WITH p, l ORDER BY l.prioridad DESC LIMIT 1
    OPTIONAL MATCH (l)-[:PERTENECE_A_GRUPO]->(g:GrupoLinea)
    OPTIONAL MATCH (ri:CapacidadRAM {gb: $ram_informada})
    OPTIONAL MATCH (r:CapacidadRAM {gb: $ram_final})
    MATCH (cd:CriterioExperto {nombre: 'descuento_negociacion'}), (cs:CriterioExperto {nombre: 'reval_ssd'})
    WITH p, l, g, ri, r, cd, cs,
         CASE WHEN p.valor_ref_ars IS NOT NULL AND l IS NOT NULL AND r IS NOT NULL
              THEN p.valor_ref_ars * l.factor_precio * r.factor END AS valor_mercado
    RETURN p {.nombre, .familia, .gama, .anio, .soporte_w11, .valor_ref_ars, .n_muestras,
              .fuente_valor, .estado_validacion} AS procesador,
           l {.nombre, .marca, .factor_precio, .origen_factor, .estado_validacion} AS linea,
           g {.nombre, .dias_promedio_venta, .indice_repuestos} AS grupo,
           ri IS NOT NULL AS ram_informada_existe,
           r {.gb, .factor} AS ram,
           valor_mercado,
           CASE WHEN valor_mercado IS NULL THEN null
                ELSE toInteger(round((valor_mercado * (1 - cd.valor / 100.0)
                                      + CASE WHEN $hdd_a_ssd THEN cs.valor ELSE 0 END) / 1000.0)) * 1000
           END AS vma

Consulta 2 — inferencia Mamdani de riesgo de obsolescencia (SM2-RIE)

            WITH $antiguedad AS antiguedad, $repuestos AS repuestos, $win11 AS win11
            MATCH (r:ReglaDifusa {base:'SM2-RIE'})-[a:ANTECEDENTE]->(cj:ConjuntoDifuso)<-[:TIENE_CONJUNTO]-(var:VariableDifusa)
            WITH antiguedad, repuestos, win11, r, a.grupo AS grupo,
                 max(CASE cj.tipo
                       WHEN 'crisp' THEN CASE WHEN (CASE var.nombre WHEN 'Soporte_W11' THEN win11 END) = cj.valor THEN 1.0 ELSE 0.0 END
                       ELSE exp(-0.5 * (((CASE var.nombre WHEN 'Antiguedad_Hardware' THEN antiguedad ELSE repuestos END) - cj.c) / cj.sigma)^2)
                     END) AS mu_grupo
            WITH antiguedad, repuestos, win11, r, min(mu_grupo) AS fuerza
            WHERE fuerza >= 0.01
            MATCH (r)-[:CONSECUENTE]->(sal:ConjuntoDifuso)<-[:TIENE_CONJUNTO]-(vs:VariableDifusa {nombre:'Riesgo_Obsolescencia'})
            WITH vs, collect({regla: r.id, fuerza: fuerza, c: sal.c, sigma: sal.sigma}) AS reglas
            UNWIND range(0, 100) AS i
            WITH vs, reglas, vs.min + (vs.max - vs.min) * i / 100.0 AS y
            UNWIND reglas AS rg
            WITH vs, reglas, y, rg, exp(-0.5 * ((y - rg.c) / rg.sigma)^2) AS mu_sal
            WITH vs, reglas, y, max(CASE WHEN rg.fuerza < mu_sal THEN rg.fuerza ELSE mu_sal END) AS altura
            WITH vs, reglas, sum(y * altura) / sum(altura) AS centroide
            MATCH (vs)-[:TIENE_CONJUNTO]->(s:ConjuntoDifuso)
            WITH reglas, centroide, s, exp(-0.5 * ((centroide - s.c) / s.sigma)^2) AS mu
            ORDER BY mu DESC
            WITH reglas, centroide, collect(s.etiqueta)[0] AS categoria
            RETURN round(centroide, 4) AS centroide, categoria

c) Diseño del flujo de orquestación

El flujo sigue el patrón sándwich con dos prompts separados. El enrutador (System Prompt maestro, común a todo el asistente) decide que la consulta corresponde a SM2; el prompt de extracción la convierte en JSON estricto; ese JSON se valida contra el texto original y alimenta las consultas Cypher sobre Neo4j; el resultado estructurado vuelve al LLM con el prompt de explicación, que solo puede redactar con esos datos.

d) Diseño de prompts

System Prompt maestro de enrutamiento (común al asistente)

Sos el enrutador de EvalTIC, un asistente que evalúa notebooks usadas para reventa.
Tu única tarea es clasificar el mensaje del usuario en UNA intención. No respondas la consulta.
Límites: el conocimiento experto (precios, costos, umbrales y reglas) está en la base de conocimiento Neo4j;
vos nunca das valores ni recomendaciones propias.

Intenciones posibles:
- "evaluacion_integral": un aviso o una oferta de venta de una notebook con precio pedido, o la pregunta
  de si conviene comprarla. Usa los tres submódulos (técnico, comercial y decisión).
- "diagnostico_tecnico": preguntas sobre el estado físico o la reparación de una notebook (batería, temperatura,
  RAM, disco, pantalla, teclado, cargador, fallas) SIN precio de compra. Submódulo SM1.
- "valuacion_comercial": preguntas sobre cuánto vale o a cuánto se revende una notebook según su procesador,
  marca/línea o RAM, SIN pedir una decisión de compra. Submódulo SM2.
- "fuera_de_dominio": cualquier otra cosa (otros productos, charla general, pedidos sin relación).

Respondé ÚNICAMENTE un JSON: {"intencion": "<una de las cuatro>", "motivo": "<frase corta>"}

System Prompt de extracción (PROMPT_EXTRACCION_SM2)

Extraé en un único objeto JSON los datos comerciales de la notebook que figuran en el mensaje.
Si un dato NO aparece, poné null. No inventes valores ni completes modelos de procesador que no estén escritos.
No agregues texto fuera del JSON.
Campos:
- "marca", "modelo": string o null
- "procesador": procesador copiado textual del mensaje o null
- "ram_gb": entero o null
- "tipo_disco": "HDD" o "SSD" o null
- "anio_fabricacion": entero o null
- "soporte_windows_11": bool o null
Respondé ÚNICAMENTE el JSON.

System Prompt de explicación (PROMPT_EXPLICACION_SM2)

Sos el tasador de EvalTIC. Explicá al usuario, en español claro y en menos de 120 palabras,
cuánto vale su notebook en el mercado de usados y por qué. Usá ÚNICAMENTE los datos del resultado que te paso
(vienen de la base de conocimiento Neo4j): valor de referencia del procesador y cantidad de avisos relevados,
factor de la línea, factor de la RAM, valor de mercado, VMA, riesgo de obsolescencia y demanda.
No inventes precios ni factores. Si el resultado está pendiente o con error, explicá qué dato falta.
Aclarás en una frase que los valores son provisionales (relevamiento de Mercado Libre del 9/11/2026).

Los ejemplos de entrada y de salida de ambos prompts están en la sección f) (columnas "Información extraída" y "Respuesta generada"), tomados de ejecuciones reales.

e) Implementación desarrollada

consultar_sm2() extrae con el prompt de SM2, valida el procesador contra el texto (descarta modelos que el LLM completa), ejecuta ejecutar_motor_sm2() y redacta con el prompt de explicación. La valuación entera (identificación de procesador, línea, grupo y RAM por expresiones regulares, y cálculo del VMA) es una sola consulta Cypher:

VMA = valor_ref(procesador) × factor(línea) × factor(RAM final) × (1 − CE-30 descuento de negociación)
      + CE reval_ssd (si SM1 planifica cambiar HDD por SSD)

Después, la lógica difusa encadenada en Cypher estima el riesgo de obsolescencia (antigüedad, índice de repuestos del grupo y soporte de Windows 11) y la demanda (riesgo y días de rotación del grupo). Política de datos: lo que el aviso menciona y no existe en el grafo da error; lo que falta o no tiene evidencia suficiente queda pendiente.

Se probaron entradas absurdas, incompletas o fuera del conocimiento cargado. El sistema nunca rellena un dato faltante con un valor favorable: o pide aclaración, o responde que está fuera de dominio, o corta con un error que dice qué falta en la base de conocimiento.

h) Análisis de explicabilidad

  • Del grafo provienen todos los valores con los que se decide: criterios expertos (con id, versión y estado de validación), costos de reparación, reglas difusas, valores de procesadores, factores de línea y de RAM, y las propias reglas de enrutamiento de datos pendientes.
  • El LLM genera solo dos cosas: el JSON de entrada (a partir del texto del usuario) y la redacción de la respuesta. No calcula ni decide.
  • Para evitar que invente criterios: (1) el prompt de explicación le prohíbe usar datos que no estén en el resultado; (2) un control anti-alucinación compara cada número de la respuesta con el resultado de Neo4j y, si aparece uno que no está, descarta la redacción y usa una respuesta determinística; (3) los estados pendientes o con error no pasan por el LLM; (4) la traza (reglas activadas, criterios y costos usados, datos inferidos y pendientes) acompaña cada respuesta y se muestra en la interfaz.

i) Limitaciones y mejoras

  • El LLM local (1,5 B parámetros) a veces completa datos que no están en el aviso o mete cosas positivas como "fallas"; se mitiga con validaciones contra el texto y el control anti-alucinación, pero un modelo más grande (o Groq) mejoraría la extracción.
  • Todos los criterios, costos y factores son provisionales: falta la entrevista de validación con el experto (M. Romero), por eso las decisiones salen como "Provisional".
  • Los precios relevados son precios pedidos, no de venta; el CE-30 (10 %) aproxima la negociación.
  • Varios procesadores tienen menos de 3 avisos y quedan pendientes; hay que ampliar el relevamiento (idealmente con un script offline que actualice el CSV, no scraping en tiempo real, para mantener la reproducibilidad).
  • El factor de RAM es una estimación del grupo; con más datos podría calibrarse igual que la línea.
