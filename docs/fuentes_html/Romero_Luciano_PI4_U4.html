b) Revisión de consultas y conocimiento recuperable

SM3 recibe el costo de SM1 y el VMA, el riesgo y la demanda de SM2, y decide con criterios del grafo: R3.7 (costo / VMA > CE ratio_reparacion_max), R3.8 (riesgo Alto y demanda Baja), margen requerido con orden fijo (CE margen_base → R3.4 o R3.5 → R3.6) y la conveniencia difusa SM3-CONV (brecha de margen y descuento necesario). Además coordina la evaluación integral: el enrutador, la extracción integral y el dictamen.

Consulta — inferencia Mamdani de conveniencia (SM3-CONV) en Cypher

            WITH $brecha AS brecha, $descuento AS descuento
            MATCH (r:ReglaDifusa {base:'SM3-CONV'})-[a:ANTECEDENTE]->(cj:ConjuntoDifuso)<-[:TIENE_CONJUNTO]-(var:VariableDifusa)
            WITH brecha, descuento, r, a.grupo AS grupo,
                 max(exp(-0.5 * (((CASE var.nombre WHEN 'Brecha_Margen' THEN brecha ELSE descuento END) - cj.c) / cj.sigma)^2)) AS mu_grupo
            WITH brecha, descuento, r, min(mu_grupo) AS fuerza
            MATCH (r)-[:CONSECUENTE]->(sal:ConjuntoDifuso)
            WITH brecha, descuento, collect({regla: r.id, fuerza: fuerza, c: sal.c, sigma: sal.sigma}) AS reglas
            UNWIND range(0, 100) AS i
            WITH brecha, descuento, reglas, i / 100.0 AS y
            UNWIND reglas AS rg
            WITH brecha, descuento, reglas, y, rg, exp(-0.5 * ((y - rg.c) / rg.sigma)^2) AS mu_sal
            WITH brecha, descuento, reglas, y,
                 max(CASE WHEN rg.fuerza < mu_sal THEN rg.fuerza ELSE mu_sal END) AS altura
            WITH brecha, descuento, reglas, sum(y * altura) / sum(altura) AS centroide
            MATCH (:VariableDifusa {nombre:'Conveniencia'})-[:TIENE_CONJUNTO]->(s:ConjuntoDifuso)
            WITH brecha, descuento, reglas, centroide, s,
                 exp(-0.5 * ((centroide - s.c) / s.sigma)^2) AS mu
            ORDER BY mu DESC
            WITH brecha, descuento, reglas, centroide, collect(s.etiqueta)[0] AS categoria
            RETURN round(centroide, 4) AS centroide, categoria

c) Diseño del flujo de orquestación

El flujo sigue el patrón sándwich con dos prompts separados. El enrutador (System Prompt maestro, común a todo el asistente) decide que la consulta corresponde a SM3; el prompt de extracción la convierte en JSON estricto; ese JSON se valida contra el texto original y alimenta las consultas Cypher sobre Neo4j; el resultado estructurado vuelve al LLM con el prompt de explicación, que solo puede redactar con esos datos.

d) Diseño de prompts

System Prompt maestro de enrutamiento (común al asistente)

Sos el enrutador de EvalTIC, un asistente que evalúa notebooks usadas para reventa.
Tu única tarea es clasificar el mensaje del usuario en UNA intención. No respondas la consulta.
Límites: el conocimiento experto (precios, costos, umbrales y reglas) está en la base de conocimiento Neo4j;
vos nunca das valores ni recomendaciones propias.

Intenciones posibles:
- "evaluacion_integral": un aviso o una oferta de venta de una notebook con precio pedido, o la pregunta
  de si conviene comprarla. Usa los tres submódulos (técnico, comercial y decisión).
- "diagnostico_tecnico": preguntas sobre el estado físico o la reparación de una notebook (batería, temperatura,
  RAM, disco, pantalla, teclado, cargador, fallas) SIN precio de compra. Submódulo SM1.
- "valuacion_comercial": preguntas sobre cuánto vale o a cuánto se revende una notebook según su procesador,
  marca/línea o RAM, SIN pedir una decisión de compra. Submódulo SM2.
- "fuera_de_dominio": cualquier otra cosa (otros productos, charla general, pedidos sin relación).

Respondé ÚNICAMENTE un JSON: {"intencion": "<una de las cuatro>", "motivo": "<frase corta>"}

System Prompt de extracción (PROMPT_EXTRACTOR_INTEGRAL)

Extrae en un único objeto JSON los parámetros de la notebook para el sistema EvalTIC.
El LLM se encarga única y exclusivamente de parsear los datos presentes en el texto a formato JSON.
No inventes valores. Si un dato NO aparece en el texto, poné null.
No agregues comentarios en el JSON (no uses // ni /* */).
NO clasifiques ni catalogues fallas críticas: incluye en "fallas" TODAS las fallas, roturas, faltantes, deterioros o problemas informados en el texto.

Campos del JSON:
- "marca": marca comercial (string o null)
- "modelo": modelo comercial (string o null)
- "procesador": procesador copiado textual del aviso, sin completar modelos que no estén escritos (o null)
- "precio_publicado": precio entero en pesos (ej: "$115.000" -> 115000) o null
- "anio_fabricacion": año entero (ej: 2020) o null
- "salud_bateria_pct": entero 0-100 o null
- "ciclos_bateria": entero o null
- "temperatura_cpu_c": entero °C o null
- "thermal_throttling": bool o null
- "ram_gb": entero (4, 8, 16) o null
- "tipo_disco": "HDD" o "SSD" o null
- "pantalla_danada": true solo si el aviso dice que la pantalla está dañada; false si dice que está bien; si no, null
- "teclado_danado": true solo si el aviso dice que el teclado está dañado; false si dice que está bien; si no, null
- "cargador_incluido": bool o null
- "soporte_windows_11": bool o null
- "fallas": lista con TODAS las fallas, daños, desgastes o problemas reportados (lista de strings). NO incluyas cosas que están bien.

Ejemplo:
Texto: "Vendo Acer Aspire 5 2020 i5 w11 $115.000. Batería 42% 780 ciclos, calienta 92C cuelgues térmicos, 4GB RAM, HDD 500GB, pantalla con rayas, teclado roto, sin cargador."

Responde ÚNICAMENTE el objeto JSON.

System Prompt de explicación (PROMPT_SINTESIS_GERENCIAL)

Eres el Director General de EvalTIC (PG3), sistema neuro-simbólico de evaluación y tasación de notebooks usadas.
A partir del resumen consolidado de la evaluación técnica (SM1), comercial (SM2) y financiera (SM3), redacta una síntesis ejecutiva comercial profesional, no determinista y concisa (máximo 120 palabras).

La síntesis ejecutiva debe incluir:
1. Veredicto Final claro: COMPRAR DIRECTO, NEGOCIAR CON CONTRAOFERTA, DESCARTAR POR INVIABILIDAD / RIESGO, o VERIFICAR ANTES DE DECIDIR.
2. Resumen Técnico (SM1): condición del equipo, todas las fallas reportadas y plan de reacondicionamiento necesario con sus costos.
3. Valuación y Mercado (SM2): VMA tasado, nivel de riesgo y demanda comercial.
4. Estrategia Financiera (SM3): márgenes proyectados, contraoferta sugerida si aplica o motivo de descarte/verificación.

Reglas:
- Mencioná textualmente todas las fallas y problemas informados en el resumen.
- Utilizá los valores numéricos y montos provistos en el resumen, sin inventar cifras.
- Redactá con estilo profesional, ejecutivo y directo, sin formato JSON ni etiquetas markdown innecesarias.

Los ejemplos de entrada y de salida de ambos prompts están en la sección f) (columnas "Información extraída" y "Respuesta generada"), tomados de ejecuciones reales.

e) Implementación desarrollada

asistente_evaltic() es el punto de entrada único: el System Prompt maestro clasifica la consulta y, si es un aviso con precio, evaluar_publicacion_integral() ejecuta: extracción con PROMPT_EXTRACTOR_INTEGRAL, validaciones contra el texto (precio, procesador, año), R3.3 (señales de bloqueo → verificación pendiente), SM1, SM2 y ejecutar_motor_sm3(). El estado de la decisión es Firme solo si todos los criterios y costos usados están validados y no hubo datos inferidos ni pendientes; si no, Provisional con la lista de criterios pendientes. El dictamen lo redacta el LLM con PROMPT_SINTESIS_GERENCIAL a partir del resumen ya calculado, con el control anti-alucinación y un dictamen determinístico de respaldo.

margen neto  = (VMA − precio − costo de reparación) / VMA
contraoferta = VMA − costo de reparación − VMA × margen requerido

En la última versión la política financiera completa se lee del grafo: el margen requerido se arma por etapas declaradas (base, después R3.4 o R3.5, después R3.6, con operaciones de asignar, máximo y sumar), el filtro de R3.7 aporta el campo y el comparador del ratio de reparación, las categorías de R3.8 salen de los conjuntos difusos, y la correspondencia entre conveniencia y decisión o contraoferta también es dato. La clasificación Firme/Provisional consulta reglas y condiciones sobre los criterios, costos e inferencias efectivamente registrados en la traza. No hay umbrales nuevos en Python; la aritmética fina sigue siendo mecanismo de ejecución.

h) Análisis de explicabilidad

  • Del grafo provienen todos los valores con los que se decide: criterios expertos (con id, versión y estado de validación), costos de reparación, reglas difusas, valores de procesadores, factores de línea y de RAM, y las propias reglas de enrutamiento de datos pendientes.
  • El LLM genera solo dos cosas: el JSON de entrada (a partir del texto del usuario) y la redacción de la respuesta. No calcula ni decide.
  • Para evitar que invente criterios: (1) el prompt de explicación le prohíbe usar datos que no estén en el resultado; (2) un control anti-alucinación compara cada número de la respuesta con el resultado de Neo4j y, si aparece uno que no está, descarta la redacción y usa una respuesta determinística; (3) los estados pendientes o con error no pasan por el LLM; (4) la traza (reglas activadas, criterios y costos usados, datos inferidos y pendientes) acompaña cada respuesta y se muestra en la interfaz.

i) Limitaciones y mejoras

  • El LLM local (1,5 B parámetros) a veces completa datos que no están en el aviso o mete cosas positivas como "fallas"; se mitiga con validaciones contra el texto y el control anti-alucinación, pero un modelo más grande (o Groq) mejoraría la extracción.
  • Todos los criterios, costos y factores son provisionales: falta la entrevista de validación con el experto (M. Romero), por eso las decisiones salen como "Provisional".
  • El riesgo influye en la demanda y en el margen requerido (R3.5/R3.8); conviene revisar con el experto si no se penaliza dos veces.
  • R3.1b (rechazo comercial directo) no está implementada.
  • Mejora: guardar cada evaluación en el grafo como historial auditable.
