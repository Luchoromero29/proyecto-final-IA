b) Revisión de consultas y conocimiento recuperable

SM1 consulta en Neo4j los nodos :CriterioExperto (umbrales, por ejemplo bateria_reemplazo y ram_objetivo), :CostoReparacion (8 tareas con su costo) y la base difusa SM1-BAT / SM1-TER (:ReglaDifusa-[:ANTECEDENTE]->:ConjuntoDifuso). La salida es un plan de reacondicionamiento con costo total, las reglas activadas y los datos que faltan verificar.

MATCH (c:CostoReparacion) RETURN c.tarea AS tarea, c.id AS id, c.costo_ars AS costo,

Consulta 2 — inferencia Mamdani de batería (SM1-BAT) en Cypher

            WITH $salud AS salud, $ciclos AS ciclos
            MATCH (r:ReglaDifusa {base:'SM1-BAT'})-[a:ANTECEDENTE]->(cj:ConjuntoDifuso)<-[:TIENE_CONJUNTO]-(var:VariableDifusa)
            WITH salud, ciclos, r, a.grupo AS grupo,
                 max(exp(-0.5 * (((CASE var.nombre WHEN 'Salud_Bateria' THEN salud ELSE ciclos END) - cj.c) / cj.sigma)^2)) AS mu_grupo
            WITH salud, ciclos, r, min(mu_grupo) AS fuerza
            WHERE fuerza >= 0.01
            MATCH (r)-[:CONSECUENTE]->(sal:ConjuntoDifuso)<-[:TIENE_CONJUNTO]-(vs:VariableDifusa {nombre:'Necesidad_Intervencion'})
            WITH vs, collect({regla: r.id, fuerza: fuerza, c: sal.c, sigma: sal.sigma}) AS reglas
            UNWIND range(0, 100) AS i
            WITH vs, reglas, vs.min + (vs.max - vs.min) * i / 100.0 AS y
            UNWIND reglas AS rg
            WITH vs, reglas, y, rg, exp(-0.5 * ((y - rg.c) / rg.sigma)^2) AS mu_sal
            WITH vs, reglas, y, max(CASE WHEN rg.fuerza < mu_sal THEN rg.fuerza ELSE mu_sal END) AS altura
            WITH vs, reglas, sum(y * altura) / sum(altura) AS centroide
            MATCH (vs)-[:TIENE_CONJUNTO]->(s:ConjuntoDifuso)
            WITH reglas, centroide, s, exp(-0.5 * ((centroide - s.c) / s.sigma)^2) AS mu
            ORDER BY mu DESC
            WITH reglas, centroide, collect(s.etiqueta)[0] AS categoria
            RETURN round(centroide, 4) AS centroide, categoria

c) Diseño del flujo de orquestación

El flujo sigue el patrón sándwich con dos prompts separados. El enrutador (System Prompt maestro, común a todo el asistente) decide que la consulta corresponde a SM1; el prompt de extracción la convierte en JSON estricto; ese JSON se valida contra el texto original y alimenta las consultas Cypher sobre Neo4j; el resultado estructurado vuelve al LLM con el prompt de explicación, que solo puede redactar con esos datos.

d) Diseño de prompts

System Prompt maestro de enrutamiento (común al asistente)

Sos el enrutador de EvalTIC, un asistente que evalúa notebooks usadas para reventa.
Tu única tarea es clasificar el mensaje del usuario en UNA intención. No respondas la consulta.
Límites: el conocimiento experto (precios, costos, umbrales y reglas) está en la base de conocimiento Neo4j;
vos nunca das valores ni recomendaciones propias.

Intenciones posibles:
- "evaluacion_integral": un aviso o una oferta de venta de una notebook con precio pedido, o la pregunta
  de si conviene comprarla. Usa los tres submódulos (técnico, comercial y decisión).
- "diagnostico_tecnico": preguntas sobre el estado físico o la reparación de una notebook (batería, temperatura,
  RAM, disco, pantalla, teclado, cargador, fallas) SIN precio de compra. Submódulo SM1.
- "valuacion_comercial": preguntas sobre cuánto vale o a cuánto se revende una notebook según su procesador,
  marca/línea o RAM, SIN pedir una decisión de compra. Submódulo SM2.
- "fuera_de_dominio": cualquier otra cosa (otros productos, charla general, pedidos sin relación).

Respondé ÚNICAMENTE un JSON: {"intencion": "<una de las cuatro>", "motivo": "<frase corta>"}

System Prompt de extracción (PROMPT_EXTRACCION_SM1)

Extraé en un único objeto JSON los datos técnicos de la notebook que figuran en el mensaje.
Si un dato NO aparece, poné null. No inventes valores. No agregues texto fuera del JSON.
Campos:
- "marca", "modelo": string o null
- "salud_bateria_pct": entero 0-100 o null
- "ciclos_bateria": entero o null
- "temperatura_cpu_c": entero °C o null
- "thermal_throttling": bool o null
- "ram_gb": entero o null
- "tipo_disco": "HDD" o "SSD" o null
- "pantalla_danada": true/false/null
- "teclado_danado": true/false/null
- "cargador_incluido": bool o null
- "fallas": lista de fallas o problemas informados (strings); [] si no hay
Respondé ÚNICAMENTE el JSON.

System Prompt de explicación (PROMPT_EXPLICACION_SM1)

Sos el técnico de EvalTIC. Explicá al usuario, en español claro y en menos de 120 palabras,
el diagnóstico técnico de su notebook. Usá ÚNICAMENTE los datos del resultado que te paso (vienen de la base de
conocimiento Neo4j): reparaciones del plan con su costo, reglas que se activaron y datos que faltan verificar.
No inventes costos, umbrales ni reparaciones. Si hay datos pendientes, pedí que se verifiquen.
Aclarás en una frase que los costos son provisionales (todavía no validados por el experto).

Los ejemplos de entrada y de salida de ambos prompts están en la sección f) (columnas "Información extraída" y "Respuesta generada"), tomados de ejecuciones reales.

e) Implementación desarrollada

Prototipo en Python (app/orquestador_evaltic.py): consultar_sm1() llama al LLM con el prompt de extracción, ejecuta ejecutar_motor_sm1() (reglas R1.1 y R1.2, plan de upgrades, inferencias difusas inferir_sm1_bat_cypher e inferir_sm1_ter_cypher que corren dentro de Neo4j) y redacta con el prompt de explicación. El LLM se usa por HTTP con Ollama (local, sin costo ni datos que salgan de la máquina); Neo4j con el driver oficial. Se eligió Python puro sin LangChain porque el flujo es fijo y así cada paso queda visible y auditable. Todo corre con docker compose (Neo4j, carga del grafo y la app).

  • Una falla insalvable (CPU/placa quemada, sin video) dispara R1.1 → inviabilidad física.
  • Una falla redactada en positivo ("pantalla perfecta") no genera reparación.
  • La mano de obra se suma al plan pero no cuenta como intervención (para R3.6 de SM3).

En la última versión la resolución técnica se resolvió por completo en Cypher y se incorporó al grafo el conocimiento de diagnóstico (B2): síntomas, diagnósticos, intervenciones y sus costos, con los criterios CE-31 y CE-32. Un síntoma sin diagnóstico registrado ya no se interpreta como reparación: deja la evaluación en VerificacionPendiente por R3.3c, y sólo la evidencia que aporta el operador por un canal separado puede liberarla. El caso de temperatura distingue throttling falso (caída 0), verdadero y ausente, cada uno con su criterio. Ese conocimiento se aplica con las semillas aditivas del repositorio mediante scripts/base_mejoras.sh, sin recargar el mercado.

Tratamiento de datos ausentes

El motor no completa con valores numéricos los datos que el aviso no informa. Cada ausencia tiene un tratamiento declarado en la base de conocimiento y visible en la respuesta:

Temperatura ausente. Si no se informa la temperatura ni el throttling, no se asume ninguna caída: el dato queda como pendiente («Temperatura bajo carga (prueba de estrés)») y no se cobra ningún servicio térmico sin evidencia. El mapeo de los tres estados —throttling falso, verdadero y ausente— sale de los criterios CE-31 y CE-32 del grafo.

Ciclos de batería ausentes. Si se informa la salud pero no los ciclos, la regla crisp SM1-BAT-CRISP reemplaza la batería cuando la salud está por debajo de CE-01 (bateria_reemplazo). El sistema no inventa un número de ciclos: el supuesto está declarado como dato en el grafo (nodo SupuestoOperativo SUP-SM1-BAT-CICLOS, estado Provisional) y la respuesta lo informa en la línea «Datos asumidos por el motor», de forma determinística y sin depender de lo que redacte el LLM.

Verificación. Dos consultas equivalentes: con salud 60 % y sin ciclos, el plan cobra el reemplazo e informa el supuesto; con salud 60 % y 900 ciclos, no hay supuesto que informar porque el ciclo es un dato observado en el aviso.

h) Análisis de explicabilidad

  • Del grafo provienen todos los valores con los que se decide: criterios expertos (con id, versión y estado de validación), costos de reparación, reglas difusas, valores de procesadores, factores de línea y de RAM, y las propias reglas de enrutamiento de datos pendientes.
  • El LLM genera solo dos cosas: el JSON de entrada (a partir del texto del usuario) y la redacción de la respuesta. No calcula ni decide.
  • Para evitar que invente criterios: (1) el prompt de explicación le prohíbe usar datos que no estén en el resultado; (2) un control anti-alucinación compara cada número de la respuesta con el resultado de Neo4j y, si aparece uno que no está, descarta la redacción y usa una respuesta determinística; (3) los estados pendientes o con error no pasan por el LLM; (4) la traza (reglas activadas, criterios y costos usados, datos inferidos y pendientes) acompaña cada respuesta y se muestra en la interfaz.

i) Limitaciones y mejoras

  • El LLM local (1,5 B parámetros) a veces completa datos que no están en el aviso o mete cosas positivas como "fallas"; se mitiga con validaciones contra el texto y el control anti-alucinación, pero un modelo más grande (o Groq) mejoraría la extracción.
  • Todos los criterios, costos y factores son provisionales: falta la entrevista de validación con el experto (M. Romero), por eso las decisiones salen como "Provisional".
  • R1.4 (RAM soldada, limitación NoAmpliable) todavía no está implementada.
  • Las palabras clave de fallas insalvables y la asociación falla→tarea siguen en Python; deberían pasar al grafo.
  • Mejora: costos por modelo (pantallas y baterías varían mucho entre líneas).
